# Security Model: Facebook Multi-Page Publisher

This document describes the security policies, encryption architectures, access controls, and protection mechanisms designed to safeguard the Facebook Multi-Page Publisher application.

---

## 1. Token Encryption Architecture

To comply with safety rules and prevent unauthorized access to Facebook Pages, access tokens must be encrypted at rest and never exposed to unauthorized entities.

```
                  +-----------------------------------+
                  |      Encryption Key (AES-256)     |
                  |     (GCP Secret Manager / ENV)    |
                  +-----------------------------------+
                                    |
                                    v
+------------------+     +--------------------+     +------------------------+
| Plaintext Token  | --> | AES-256-GCM Cipher | --> | Base64 Encrypted String|
| (OAuth Flow API) |     |                    |     | (Saved to PostgreSQL)  |
+------------------+     +--------------------+     +------------------------+
```

### 1.1. Encryption Standard
- **Algorithm**: `aes-256-gcm` (Advanced Encryption Standard in Galois/Counter Mode).
- **Initialization Vector (IV)**: A unique, cryptographically secure random 12-byte IV generated for every encryption operation. The IV is stored alongside the ciphertext in the database.
- **Authentication Tag**: A 16-byte authentication tag generated by GCM to ensure ciphertext integrity and prevent tampering.
- **Key Storage**: The 256-bit encryption key must be loaded at runtime from a secure environment variable (e.g., GCP Secret Manager or encrypted `.env` files in production). The encryption key is **never** checked into Git.

### 1.2. Key Derivation & Rotation
- If the secret key is updated, all existing tokens must be re-encrypted or the connected profiles re-authenticated.
- Encrypted tokens are formatted as: `iv:authTag:encryptedText` to simplify storage in a single database column.

---

## 2. Token Isolation (No Browser Exposure)

To satisfy the constraint that tokens must never appear in browser code, the application implements strict data filtering layers:

- **Server-Side Exclusivity**: The frontend dashboard communicates with Next.js API endpoints. All API payloads returned to the frontend must omit `encryptedAccessToken` and `encryptedPageToken`.
- **Masking UI Details**: The client interface only receives metadata properties indicating if a connection is active (e.g., `hasValidToken: true`, `tokenExpiresAt`).
- **Worker Decoupling**: When the publishing worker runs, it retrieves tokens from the database, decrypts them in memory, and immediately forwards them in HTTPS request headers directly to Meta's APIs. The plain text token never enters local variables exposed to client responses or dashboard APIs.

---

## 3. Storage and Media Security

### 3.1. Google Cloud Storage Private Configuration
- The GCS bucket hosting videos and thumbnails is configured with **Fine-Grained IAM Access Control** and **Public Access Prevention**.
- **Signed URLs**: The Next.js API server generates short-lived, single-use PUT signed URLs (valid for 15 minutes) for client-side uploads. The client uploads media directly to GCS using these signatures.
- **Worker Access**: The background worker accesses GCS objects via official Google Application Default Credentials (ADC) or a dedicated IAM service account role with read permission. No public read URLs are generated.

### 3.2. Data Retention & Cleanup
- To minimize the risk of media exposure, the system triggers automatic cleanup of video assets from GCS 30 days after a video's status is updated to `PUBLISHED` or `FAILED`.

---

## 4. Webhook and Task Authentication

Because the worker endpoint executes publishing operations, it must verify the authenticity of scheduled trigger requests.
- **OIDC Token Verification**: When Google Cloud Tasks calls the Cloud Run worker webhook, it is configured to attach an OpenID Connect (OIDC) ID token generated by Google.
- **Worker Validation**: The worker verifies the OIDC token signature using Google's public certificates, ensuring that only the authorized Google Cloud Tasks service account is triggering the publishing webhook.

---

## 5. Log Sanitization

To ensure that sensitive details do not leak through server logs, console outputs, or error monitoring tools (e.g., Sentry):
- **API Response Filtering**: All network communication handlers wrap Graph API responses. If an error is thrown, the logger strips potential access tokens out of request URLs or error payload parameters.
- **Custom Logging Wrapper**: A custom Winston log formatter parses all log data. Any parameter matching a regex pattern of a Facebook token (`EAAC...`) is redacted and replaced with `[REDACTED]`.
